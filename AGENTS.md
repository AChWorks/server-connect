# Server Connect — contributor and Master instructions

- Start with README.md and **docs/PROJECT-SPEC.md**. The short specification owns lasting product **goals, boundaries and direction**, not issue IDs, implementation details or CI history; use the linked Architecture, Safety, Distribution and Acceptance contracts for technical detail. Do not let stale chats or obsolete Issue text silently change accepted intent.
- Reconcile current main, relevant **open Issues**, PRs, CI, release assets and tested deployment evidence. A closed Issue or prior mock is not current acceptance.
- Apply the repository-local project, architecture, safety, offline distribution, and acceptance contracts. This public repository must remain understandable without access to private company resources. Never mutate another repository without its own explicit authorization.
- Current repository mutation scope is **AChWorks/server-connect** only. Existing STL, SSO, external tunnel tools, aaPanel and customer services remain separate resource owners; preserve them.
- The active routed goal is one official sing-box **Smart Routing TUN**, not another VPN engine or per-job/PID routing system. Implement only the currently approved scope. See PROJECT-SPEC for the traffic policy and ARCHITECTURE for packet/resource boundaries.
- Author repository documentation, Issues, contributor guidance, and technical comments in English. Optional future product localization is a separate user-facing feature.
- Favor minimal native Linux/service capabilities, clear CLI+JSON contracts and a small reversible host footprint. Keep settings, secrets and runtime state out of Git.
- Never install/alter a production server, public routing, SSH/firewall/DNS or customer sites without specific current authorization. Test on disposable isolated hosts; retain console/snapshot and exact cleanup evidence.
- Any route-affecting implementation requires independent Activation Guard, running Runtime Health Guard, owned-resource rollback, tested crash/reboot recovery and mandatory negative/field evidence defined in docs/ACCEPTANCE.md.
- Changes require focused tests, exact-candidate proof appropriate to risk, and high-assurance author-separated independent review for privileged/network code before integration and release.
- Before requesting that independent review, the author must inspect the **complete effective diff** for partial-success and failure-before-flag transitions (including privileged resource creation, rollback and cleanup), check related existing paths for the same defect, add one discriminating negative regression where needed, and finish exact-candidate CI first. Do not use the reviewer as a test/debug loop or re-review unaffected code without new evidence.
- Keep documentation **single-owner and purposeful**: long-lived goals in PROJECT-SPEC, technical design/operation in specialized docs, actionable work in Issues, exact evidence in PRs/CI/releases. Preserve non-obvious valuable lessons; do not copy CI logs, issue numbers or obsolete command descriptions into the canonical spec, create unused documents or maintain chat-based snapshots.
- Follow the Distribution contract for official/mirror/offline acquisition, independent publisher trust and one shared installer; Cloudflare website ingress is a separate optional capability. Do not claim a working path, full recovery or a release before exact-artifact evidence.
